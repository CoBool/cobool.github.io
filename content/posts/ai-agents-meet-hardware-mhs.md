AI 에이전트가 파일을 읽고, 코드를 수정하고, API를 호출하는 장면은 이제 꽤 익숙하다.

하지만 에이전트가 현미경과 로봇 팔, 액체 분주기, 양자컴퓨터의 레이저를 직접 제어하기 시작하면 이야기가 달라진다.

Anthropic은 2026년 8월 27일 [Model Hardware Standard(MHS) 연구 프리뷰](https://www.anthropic.com/news/model-hardware-standard-research-preview)를 공개했다. MHS는 AI 에이전트가 서로 다른 물리 장비를 공통 방식으로 발견하고, 상태를 읽고, 명령을 내릴 수 있도록 하는 표준화된 인터페이스를 목표로 한다.

아직 공개 표준이 완성된 단계는 아니다. Anthropic도 현재 버전을 연구 프리뷰로 한정하고 있고, 안전 평가와 운영 경험을 쌓은 뒤 오픈소스로 공개할 계획이라고 밝히고 있다.

그럼에도 이 발표가 흥미로운 이유는 단순하다.

**AI 에이전트의 실행 경계가 소프트웨어 도구에서 물리 세계로 확장되고 있기 때문이다.**

## MHS는 무엇을 표준화하려는가

실험실이나 제조 현장의 장비는 대부분 서로 다른 API와 제어 방식을 가진다.

Anthropic 설명에 따르면 여러 장비를 하나의 자동화 흐름으로 묶는 작업은 장비마다 별도의 통합 코드를 작성해야 하기 때문에 수주에서 수개월이 걸릴 수 있다. MHS는 이 문제를 공통 드라이버 계층으로 줄이려 한다.

핵심 개념은 의외로 단순하다.

```text
AI Agent
   ↓
MCP / CLI / API
   ↓
MHS Driver
   ↓
Physical Device
```

MHS 드라이버는 장비마다 다른 세부 구현을 감추고 `read`, `write` 같은 기본 명령을 공통 인터페이스로 노출한다. 동시에 장비가 무엇을 측정할 수 있는지, 어떤 값을 조정할 수 있는지, 어떤 안전 한계를 가져야 하는지 같은 정보도 기계가 읽을 수 있는 형태로 제공한다.

Anthropic은 MHS가 모델에 종속되지 않으며, 에이전트가 [Model Context Protocol(MCP)](https://www.anthropic.com/news/model-hardware-standard-research-preview) 같은 표준 프로토콜을 통해 장비에 접근할 수 있다고 설명한다.

여기서 중요한 부분은 MHS가 단순한 "하드웨어용 API 규격"만을 노리는 것이 아니라는 점이다.

에이전트가 처음 보는 장비라도 동작 특성과 안전 제한을 이해할 수 있도록 **장비의 의미와 제약까지 인터페이스의 일부로 표현하려 한다.**

## MCP 다음의 문제는 실행 대상 자체다

MCP가 빠르게 주목받은 이유 중 하나는 AI 모델과 외부 도구 사이의 연결 방식을 표준화했기 때문이다.

파일 시스템, 데이터베이스, SaaS API처럼 소프트웨어 세계의 도구는 비교적 명확하다. 호출이 실패하면 다시 시도하거나 롤백할 수도 있다.

물리 장비는 그렇지 않다.

```text
파일 수정 실패
→ 다시 실행 가능

API 요청 실패
→ 재시도 가능

로봇 팔 오작동
→ 장비나 주변 환경에 실제 영향
```

그래서 하드웨어 제어에서는 "무엇을 호출할 수 있는가"보다 **어디까지 호출할 수 있는가**가 더 중요해진다.

MHS가 드라이버 수준에서 안전 한계와 장비 특성을 함께 선언하려는 이유도 여기에 있다. Anthropic은 MHS 드라이버가 장비가 측정하거나 조정할 수 있는 값과 함께 강제할 안전 제한을 에이전트에게 제공한다고 설명한다.

이 구조가 실제 표준으로 자리 잡는다면, 에이전트 시스템을 설계하는 개발자의 관심사도 달라질 가능성이 있다.

```text
기존
"모델이 어떤 tool을 호출할 수 있는가?"

↓

하드웨어 에이전트
"모델이 어떤 범위 안에서 어떤 물리적 상태를 바꿀 수 있는가?"
```

권한 관리가 API 스코프를 넘어 물리 상태의 제약 조건으로 내려가는 셈이다.

## 더 흥미로운 패턴: 에이전트가 만든 결과를 다시 결정론적 코드로 만든다

MHS 발표에서 개인적으로 가장 흥미로운 부분은 에이전트가 계속 실시간으로 장비를 제어하는 사례보다, **에이전트가 시행착오를 통해 제어 방법을 찾은 뒤 그 결과를 결정론적 코드로 남긴 사례**다.

Anthropic과 QuEra는 양자컴퓨터의 레이저를 안정된 주파수로 되돌리는 작업에 MHS를 사용했다.

QuEra의 [공식 기술 글](https://www.quera.com/blog-posts/holding-the-light-teaching-an-ai-to-lock-and-tune-our-quantum-computers-lasers)에 따르면 Claude는 실제 테스트 장비를 대상으로 여러 복구 전략을 반복 실험했고, 최종적으로 만들어진 자동 복구 컨트롤러는 700회 검증 중 695회 성공해 99.3%의 성공률을 기록했다.

중요한 것은 이 수치만이 아니다.

최종 운영 환경에서 레이저를 복구하는 것은 LLM이 매번 판단하는 에이전트 루프가 아니라 **검증 가능한 결정론적 프로그램**이다. QuEra는 MHS 환경에서 Claude가 컨트롤러를 설계하고 검증했지만, 실제 벤치에서 동작하는 결과물은 사람이 검사할 수 있는 독립 실행 코드라고 명시한다.

이 패턴은 꽤 현실적이다.

```text
Agent
  ↓
탐색 / 실험 / 최적화
  ↓
검증된 로직 생성
  ↓
Deterministic Program
  ↓
Production
```

AI 에이전트를 모든 실행 경로의 런타임으로 두는 대신, 불확실성이 큰 탐색 단계에서 사용하고 그 결과를 예측 가능한 프로그램으로 고정한다.

소프트웨어 개발에서도 비슷한 구조를 생각할 수 있다.

에이전트가 코드를 작성한다고 해서 프로덕션에서 모든 요청을 다시 LLM에게 판단시킬 필요는 없다. 에이전트가 찾은 규칙이나 최적화 결과를 테스트 가능한 코드와 설정으로 남기는 편이 더 적절한 영역이 많다.

물리 시스템에서는 이 차이가 편의성 문제가 아니라 안전성과 재현성 문제로 바로 이어진다.

## "MCP for hardware"라고 부르기에는 아직 이르다

MHS 발표 직후 Hacker News에서도 ["MCP for Hardware인가"](https://news.ycombinator.com/item?id=49468834)라는 식의 반응이 나왔다.

비유 자체는 이해하기 쉽다. 하지만 현재 단계에서 MHS를 USB나 MCP처럼 이미 정착된 범용 표준으로 보는 것은 과장이다.

Anthropic의 발표만 보더라도 몇 가지 제한이 분명하다.

- 현재는 제한된 파트너를 대상으로 한 연구 프리뷰다.
- 프로그래밍 인터페이스가 없는 장비는 바로 사용할 수 없다.
- Claude의 공간적·물리적 추론에는 여전히 한계가 있어 전문가 감독이 필요하다.
- 안전 평가와 운영 가이드도 아직 연구 중이다.
- 오픈소스 공개는 연구 프리뷰 이후로 예정되어 있다.

즉 지금 MHS의 가치는 "새 표준이 결정됐다"는 데 있지 않다.

**에이전트와 물리 장비 사이에 어떤 추상화 계층이 필요할지 구체적인 구현과 실제 사례를 내놓았다는 데 있다.**

## 개발자에게 더 중요한 질문

MHS가 실제로 널리 쓰이느냐와 별개로, 이번 발표는 에이전트 시스템을 설계할 때 앞으로 피하기 어려운 질문을 보여준다.

첫 번째는 **권한의 표현 방식**이다.

에이전트에게 장비 접근 권한을 주는 것만으로는 충분하지 않다. 허용 범위, 속도, 온도, 힘, 이동 범위 같은 제약을 실행 계층이 강제해야 한다.

두 번째는 **관찰 가능성**이다.

모델이 무엇을 판단했는지만 기록해서는 부족하다. 어떤 명령이 실제 장비에 전달됐고, 장비 상태가 어떻게 바뀌었으며, 어떤 안전 제약이 적용됐는지 추적할 수 있어야 한다.

세 번째는 **에이전트와 결정론적 코드의 경계**다.

모든 과정을 에이전트가 계속 판단하게 할 필요는 없다. 탐색과 계획에는 모델을 사용하되, 반복 실행되는 제어 로직은 검증 가능한 프로그램으로 내려보내는 구조가 더 적합할 수 있다.

마지막은 **표준화의 대상**이다.

AI 에이전트 시대의 인터페이스는 단순히 함수 이름과 파라미터만 정의하는 것으로 끝나지 않을 가능성이 크다.

장비가 무엇을 할 수 있는지뿐 아니라, **무엇을 해서는 안 되는지**도 인터페이스에 포함해야 한다.

## 에이전트의 다음 경계는 인터페이스다

최근 AI 업계의 관심은 모델 성능이나 코딩 능력에 집중되는 경우가 많다.

하지만 실제 에이전트 제품을 만들다 보면 모델 자체보다 더 오래 남는 문제가 있다.

모델이 바뀌어도 도구는 연결해야 하고, 권한은 제한해야 하고, 실행 결과는 관찰해야 한다.

MHS는 이 문제가 물리 세계로 확장됐을 때 어떤 모습이 되는지를 보여주는 초기 사례다.

아직 MHS가 사실상의 표준이 될지는 알 수 없다. 다른 규격이 등장하거나, 산업별 표준으로 분화될 수도 있다.

그래도 방향은 꽤 분명해 보인다.

**AI 에이전트가 더 많은 일을 하게 될수록 중요한 것은 모델에게 더 많은 권한을 주는 것이 아니라, 그 권한을 어떤 인터페이스와 경계 안에서 실행하게 만들 것인가다.**

소프트웨어에서는 잘못된 호출이 로그 한 줄로 끝날 수도 있다.

하드웨어에서는 그렇지 않다.

그래서 에이전트가 현실 세계로 나올수록, 결국 다시 인터페이스 설계와 안전한 경계라는 오래된 엔지니어링 문제로 돌아오게 된다.
